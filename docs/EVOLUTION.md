# 1 台の PC から AWS + GPU まで、RAG システムを 4 回作り直した話

社内ナレッジ検索の応答を **17 秒 → 840 ms** に縮めるまでに、アーキテクチャを 4 回書き直した。
1 年間の意思決定の記録と、なぜ毎回作り直す羽目になったかのリアル。

**読んでほしい人**: RAG / 社内ナレッジ検索を「PoC は動いたが本番でハマっている」または「これから自社に入れようとしている」開発責任者・CTO・1 人情シス。
**書いてる人**: [GridJapan](https://gridworld.co) — AI × 業務システムの受託開発をやっている日本の小さなエンジニアチーム。このリポジトリのコードは自社で毎日動いている実運用コードです。

進化の順番は単純で、
**「ローカル専用バッチ → 常駐デーモン → AWS サーバーレス公開 → GPU 加速」**。
どれも「目の前の問題を解くと、次の問題が見える」という連鎖で進みました。
設計図を先に描いたのではなく、使って困って作り直した記録です。

---

## Phase 1: ローカル専用・バッチ駆動 (v0.1)

### その時の目的

「1 人の PC で、Google Drive 共有フォルダを RAG 化できる」。まずは
**動くパイプライン** を作ることだけに集中した時期。

### 当時の実装

- **起動形態**: 1回実行で終わる Python スクリプト (`build_parallel.py`)
- **スケジュール**: Windows タスクスケジューラに登録した `.bat` で毎朝自動起動
- **処理単位**: 全ドライブを「今この瞬間の状態」で全件スキャン → 再構築
- **検索**: ローカル `127.0.0.1` の FastAPI を叩く管理画面のみ (Web)
- **プロセスモデル**:
  ```
  (schtasks 起動) → build_parallel.py → 全ドライブ列挙 → embed → upsert → exit
  (次回実行まで何も動かない)
  ```

### 困ったところ

- 1 日 1 回のバッチなので、**直前のドライブ変更が即反映されない**
- 巨大ドライブがあると夜間バッチが朝まで終わらず、翌日のバッチに重なる
- `.bat` が失敗しても気付きづらい（Windows のイベントログを追う羽目になる）
- タスクスケジューラが勝手に PowerShell 窓を立ち上げて鬱陶しい
- **検索は PC 前に座ってブラウザを開かないとできない**（遠隔無理）

### この段階で出た結論

**「バッチは正解じゃない」**。Drive の変更を継続的に拾って、
いつクエリしても「今の状態」が検索できる仕組みが必要。
→ デーモン化へ。

## Phase 2: 常駐デーモン化 (v0.2 〜 v0.4)

### その時の目的

RAG が **「実行時しか動かない道具」から「常に居るサービス」へ** 変わる。
タスクスケジューラの世界を卒業する。

### 当時の実装

- **起動形態**: `src.rag_daemon` を Python の常駐プロセスとして起動
- **アーキテクチャ**: 3 本のプロセスが独立して動く
  - `control_api` — Web UI + REST API (FastAPI、port 17600)
  - `rag_daemon` — 4 ワーカー並列のインデックスビルド + 差分同期
  - `desktop/` (Electron) — always-on-top ミニモニター (500ms ポーリング)
- **差分同期**: Google Drive **Changes API** で前回同期以降の変更だけを取得
  (`rotate_token` を `fd_registry` に保存)
- **ビルドは完全自動**: ユーザーが「ビルド ON」にしたドライブを、マネージャが
  ポーリングして新規・更新ファイルだけ処理
- **耐障害性**:
  - `pg_try_advisory_lock(drive_id)` でワーカー間排他
  - `zombie_cleanup` で stale なワーカー行を 30 秒ごとに GC
  - 子プロセス死亡時の復旧 (`_worker_ctx` 再構成)

### プロセスモデル

```
(毎ログオン時に手動 or NSSM 起動)
                        │
                        ▼
┌─────────────────────────────────────────────────┐
│         常駐プロセス (死なない)                   │
│                                                  │
│  control_api ─── Web UI / REST                   │
│       │                                          │
│       │ IPC                                      │
│       │                                          │
│  rag_daemon ──── 4 workers                       │
│       │           ├─ worker 1: file A を embed  │
│       │           ├─ worker 2: file B を embed  │
│       │           ├─ worker 3: file C を embed  │
│       │           └─ worker 4: file D を embed  │
│       │                                          │
│       └─→ PostgreSQL + pgvector (per-FD schema) │
└─────────────────────────────────────────────────┘
```

### この段階で出た結論

手元で常時インデックスが育っていくのは気持ち良い。
だが、**「別 PC から検索したい」という要求**が次に来た。

- 赤坂オフィスの PC にデーモンが居る
- 平井オフィスの PC で Claude Cowork を使う
- 平井の Cowork から赤坂の RAG を引きたい

VPN / SSH / トンネル は全部「ネットワーク管理タスクが永続的に増える」。
もっと軽い中継が欲しい → AWS サーバーレスへ。

## Phase 3: AWS サーバーレス公開 (v0.5)

### その時の目的

**遠隔の Claude Cowork から、赤坂の RAG に問い合わせできるようにする**。
ただし「RAG のビルド時は AWS に一切アクセスしない」（ビルド高頻度 × AWS 従量
課金は事故の元）。あくまで **パイプ** としてだけ AWS を使う。

### アーキテクチャ

```
┌──────────────┐  HTTPS POST /mcp  ┌─────────────────────────────┐
│ Hirai PC     │──────────────────▶│ AWS (ap-northeast-1)         │
│ Claude Cowork│                   │                              │
└──────────────┘                   │ ┌──────────────────────────┐ │
                                   │ │ API Gateway HTTP API     │ │
                                   │ └─────────────┬────────────┘ │
                                   │               ▼              │
                                   │ ┌──────────────────────────┐ │
                                   │ │ Lambda (mcp_handler)     │ │
                                   │ │ - Basic Auth 検証        │ │
                                   │ │ - SQS 送信 (req)         │ │
                                   │ │ - DDB ポーリング (resp) │ │
                                   │ └─────┬────────────▲──────┘ │
                                   │       │            │         │
                                   │       ▼            │         │
                                   │ ┌─────────┐  ┌────────────┐  │
                                   │ │   SQS   │  │ DynamoDB   │  │
                                   │ │(request)│  │ (response) │  │
                                   │ └────┬────┘  └──────▲─────┘  │
                                   │      │              │         │
                                   └──────┼──────────────┼─────────┘
                                          │ long-poll    │ put
                                          ▼              │
                                  ┌──────────────────────┴──────┐
                                  │  Akasaka PC                  │
                                  │  aws_bridge (常駐 Python)   │
                                  │    SQS.receive → RAG 実行   │
                                  │    → DDB.put                 │
                                  └──────────────────────────────┘
```

### 仕掛け

- **Akasaka PC から AWS に outbound 接続** (SQS long poll) しかしないので、
  オフィスの NAT 内に居ても穴あけ不要
- **Lambda は synchronous** (API Gateway の 30 秒タイムアウト内に SQS 送信
  + DDB ポーリング完了)
- **Basic Auth** は Lambda の `BASIC_PASS` 環境変数で検証。パスワードは
  `terraform.tfvars` にだけ置き、**Git には載せない**
- **使った時だけ料金** (月 10 クエリで $0.10 以下)

### 困ったところ

最初のクエリが毎回遅い。

```
1 回目: 17 秒  (cold)
2 回目: 840 ms (warm)
```

17 秒は **embedding モデル + リランカーモデルの初回 CPU ロード**。
280M パラメータ の xlm-roberta を CPU で動かしているせいで
そもそも 1 embedding あたり数秒かかっている。並列化しても
**1 ワーカーあたり 1 コア (OMP_NUM_THREADS=1)** で CPU が詰まる。

→ GPU 加速へ。

## Phase 4: GPU 実装 (v0.6)

### その時の目的

**「検索 UX を秒オーダーではなくミリ秒オーダーにする」**。
赤坂 PC に積まれていた RTX 4070 SUPER (12 GB VRAM) を使い倒す。

### 発見の連鎖

- `torch=2.11.0+cpu` が入っていた（pip のデフォルト挙動）
- `torch.cuda.is_available()` → `False`
- 物理 GPU は生きている (nvidia-smi は正常、driver 595.79, CUDA 13.2)
- → **PyTorch の CPU ビルドが足を引っ張っていた**

### 置き換え

```
pip uninstall torch -y
pip install torch==2.6.0 --index-url https://download.pytorch.org/whl/cu124
```

`EMBEDDING_DEVICE=auto` は既に `_pick_device()` で
`torch.cuda.is_available()` を見るように書かれていたので、
**コード変更はゼロ**。デーモン再起動だけで GPU に切り替わった。

### 実測値（同じクエリ、同じ DB）

| | CPU only (OMP=1) | **GPU (RTX 4070 SUPER)** | 改善倍率 |
|---|---|---|---|
| search warm  | 3〜13 秒  | **840 ms**  | **4〜15 倍** |
| search cold  | 23 秒     | 17.7 秒     | 1.3 倍 |
| フルビルド (221 files) | 6〜8 分 | 5 分 | 1.2〜1.6 倍 |
| GPU 使用率 ピーク | — | 78%  | — |
| VRAM (ピーク)  | — | 7 GB  | 12 GB 中 |
| 消費電力 (推論中) | CPU 200W 級 | 122W | ワット効率も改善 |

### 本当に効いた場所

面白かったのは「**ビルドより検索が劇的に速くなった**」こと。

ビルドは Google Drive API （Sheets/Docs/PDF）の I/O が支配的だった。
埋め込み計算を GPU にしても、API のレスポンス待ちが大半なので
Amdahl の法則で頭打ち。

一方 **検索時のリランカー** (BAAI/bge-reranker-v2-m3) は、
候補 50 件 × クエリのペアを cross-encoder に通す処理が
CPU で重かった。これが GPU で一気に捌けるようになり、
warm 検索が 3 秒から 840ms に。

### この段階で出た結論

**UX が変わると使い方も変わる**。
Cowork から RAG を呼ぶのが「1 回だけの慎重なクエリ」から
「思いついたら投げる対話型クエリ」になった。
秒を待つ検索と、即座に返ってくる検索は質的に違う。

## 振り返り

```
  v0.1                v0.2-0.4              v0.5                  v0.6
  ────                ────────              ────                  ────
  1 回実行            常駐プロセス          外の世界から          GPU で
  バッチ              差分同期              ミリ秒で呼べる        応答を早く
  (PC の前)           (常に最新)            (どこからでも)        (待たない)

  ┌──┐                ┌────┐                ┌─────┐               ┌─────┐
  │  │   ───▶         │████│    ───▶        │████△│     ───▶      │████⚡│
  │  │                │████│                │████△│               │████⚡│
  └──┘                └────┘                └─────┘               └─────┘
  ローカル            常駐                  パブリック             GPU
```

各フェーズは、**「前フェーズの制約が限界に見えた瞬間」** に生まれました。

- Phase 1 → 2: タスクスケジューラが起動する PowerShell 窓の鬱陶しさ、反応の遅さ
- Phase 2 → 3: 遠隔 PC から検索したい、VPN は重い
- Phase 3 → 4: CPU embedding がユーザー体験のボトルネック

どれも「大きな設計を決めてから作る」ではなく、
「動かしたものを使ってみて、次に欲しいものが見える」サイクルでした。
